# Architecture

Read this next to `capability-map.html` (open in a browser). The map is the
picture; this is the walk-through.

## The shape

Four layers, left to right on the map.

1. Browser hub (`web/index.html`). A single page, four panes: conversation with
   push-to-talk on the left half, a tool artifact pane top-right, a Cesium globe
   bottom-right, and a FITS viewer that shares the bottom-right stack via each
   pane's expand-to-full control. The hub only talks to the orchestrator; it
   never calls a tool or the model directly.

2. Orchestrator (`orchestrator/server.py`), FastAPI on `:8703`. It is the only
   backend. It takes a turn, runs the tool loop, and returns text + an artifact,
   plus synthesized speech on the voice path. It also serves the hub and the
   viz/image routes.

3. Tool adapters (`orchestrator/tools/`). Each adapter implements one contract
   (`contract.py`) and wraps one external tool. The orchestrator offers their
   schemas to the model and dispatches by name. This layer is the reusable
   asset: the contract is stable, the tools behind it are swappable.

4. Fetched tools + model + data. GMAT (optional), SatSim (own TF venv),
   whisper.cpp, Piper, Aladin Lite + Cesium (browser CDN), and the model server
   (llama.cpp or Ollama). The build script fetches them; the harness points at
   them by path or URL. Propagation is the exception: the harness ships its own
   analytical propagator (`orchestrator/propagate.py`, SGP4 + two-body), so the
   globe works with nothing fetched; GMAT only raises fidelity.

The browser fetches generated bytes (FITS scenes, OEM) over `/data/ephemeris`
and `/data/scenes`, static mounts the orchestrator serves so the Aladin and
Cesium panes can load real files.

## A turn, end to end

The loop is deterministic Python (`server.py:_turn`), not model-driven control
flow, so it behaves the same whether the small model calls functions well or
badly:

1. Pass 1: send the user text plus the tool schemas to the model. If it returns
   a tool call, run that adapter; if not, its plain answer is the answer.
2. Run the chosen adapter's `run()`. On failure, the orchestrator speaks the
   error plainly rather than inventing a success.
3. `render()` turns the result into a hub artifact (a table, chart, image +
   overlay, or a "viz" signal that the globe should reload).
4. Pass 2: send the tool result back to the model with no tools, so it speaks a
   short answer grounded only in that result.
5. On the voice path, whisper transcribes the incoming WAV before step 1 and
   Piper synthesizes the reply after step 4.

## Why the globe redraws itself

A propagation writes an OEM named by object, so distinct objects accumulate as
separate files. `/viz/czml` merges ALL current OEMs into one CZML, one entity per
satellite (per-object color + label), so the globe shows every propagated object
at once, ask for another and it appends. The hub polls `/viz/files`; the head
encodes the whole set (count + newest), so adding an object or clearing changes
it and triggers a reload. No page reload, no push channel from the model.

`POST /viz/clear` resets the globe by MOVING the OEMs into a `_cleared/` subdir
(a move, never a delete), so the reset is reversible and leaves no destructive
operation in the code.

## The model seam (today local, tomorrow hosted)

`orchestrator/llm_client.py` speaks the OpenAI chat-completions API. Local
llama-server, local Ollama, and a remote hosted API are the same code with a
different `LLM_BASE_URL`. That is the one change needed to move from a local
model to a hosted backend later; nothing else in the harness changes.

## What this repo does NOT include

Any real detection or estimation method. `detector_example.py` is a teaching
stub (a MAD-sigma threshold) so the toolchain has a working detection step.
Replace it with your own detector via the same contract.
